# datafetch: A Research Retrospective and Future-Research Agenda

*Internal research report, 2026-06-16. Status: program assessment after five experimental episodes (CRAG, PokeAPI/SaC, SkillCraft, OpenTraces dark store).*

## 1. Executive summary

We set out to answer one question: can a typed dataset interface emerge automatically from agent usage, such that each successive search over a private store gets cheaper and better without anyone curating it? The honest verdict is no. Across five corpora (FinChain, CRAG, PokeAPI/SaC, SkillCraft, OpenTraces) and roughly six weeks of pre-registered, adversarially-audited evals (thesis seeded 2026-05-02, commit 4bcb6e2f0; this report 2026-06-16), frontier models do not spontaneously reuse crystallised helpers, and the strongest form of the cost thesis, cross-session amortisation, was falsified on the one valid live paired run (arm4 warm reuse cost more than arm1 inline rewrite in every token unit, M*=+Infinity, full-weight denominator -66,520.8, and was less correct at h1x 2/5 vs 4/5; commit 0665d5a27). The decisive structural finding is that cold agents over a private polymorphic store are wrong 80-90% of the time (OpenTraces G0: 8/10 naive runs wrong; plan-012 M1 side-finding: organic correctness 1/8 even with the typed mount), so raw usage is mostly noise, and auto-crystallising what the agent did would mostly promote wrong abstractions.

What did hold is narrower and real: a hand-curated, governed typed interface measurably helps on a real dark store. On the sealed OpenTraces corpus, the curated arm (armL) quadrupled per-question majority correctness over a cold mount (18.3% vs 4.8%, PRIMARY +0.1346, clustered CI [0.0385, 0.2596] excluding zero), beat a strong natural-language-recipe floor (+0.0769, CI [0.0192, 0.1538]), and was cheaper in both tokens and turns. That result is the program's first positive live paired verdict, and it survives a full supervisor recompute-audit, but it carries a real caveat: roughly 11 of 19 winning questions have empty gold, and on the 93 non-empty questions the effect shrinks to armL 8/93 vs armN 0/93. Absolute correctness is low everywhere.

One-sentence product recommendation: build datafetch as a **governed evidence layer** over verifiable-data domains, where promotion of a helper is gated not on usage frequency but on survival of a cheap independent verifier, and abandon the auto-emergence framing entirely.

## 2. The original thesis and why it was reasonable

The founding claim, seeded 2026-05-02 (commit 4bcb6e2f0) from background research on Voyage code-mode (br/01) and PySyft force-intent-declaration (br/11), was stated as: *datafetch does not virtualize the whole dataset, it virtualizes the dataset interface, then improves that interface from accepted, evidence-backed work* (kb/mission.md L15-44). Turn datafetch on over an arbitrary MongoDB Atlas store, synthesize a typed `df.*` namespace from sampling, and let the surface grow tenant-by-tenant as the agent ships accepted answers.

The mechanism was concrete and falsifiable, which is why it was worth building. The first time a question shape is asked, the agent runs cold: `mode:novel`, `tier:4`, composing four top-level calls (`findSimilar` to `pickFiling` to `inferTableMathPlan` to `executeTableMath`). An in-process observer reads the committed trajectory, crystallises a typed `lib/<tenant>/<name>.ts`, and the next similar intent runs warm: `mode:interpreted`, `tier:2`, one client-visible call. The second time a question shape is asked, the agent's program shrinks. This cold-to-warm tier flip was designated THE falsifier (kb/mission.md L62-78), and it did fire end-to-end: the first PASS landed 2026-05-06 (64/64, learned `rangeTableMetric`, commits 893369ca5/b0fa85a79). The thesis was reasonable because the loop demonstrably works. The question was never *can it crystallise* but *does crystallisation pay, and does it pay without a human in the loop*.

## 3. What we built (the instruments) and why they are credible

**The code-mode substrate.** A dataset harness, the equivalent of a browser harness but over a dataset substrate: a fixed read-only `db/` substrate, a structured `df.*` exploration surface, and an accumulation loop into a `lib/` tenant overlay (lineage br/09, br/12; project_canonical_analogy.md). Each intent runs in an ephemeral isolated query mount, a temporary git worktree over the harness, with a per-worktree HEAD pointer (result/HEAD.json) so parallel intents do not collide. The unit of learning is not a prompt or transcript but visible, committed, executable TypeScript that passed a structured `df.answer()` envelope behind nine validation gates (kb/product-design.md §1.2/§2.8), auditable by construction and cat-able.

**The OpenTraces dark-store corpus (plan 011, episode 04).** The thesis needed a corpus the model has no training prior on, where inline search is genuinely expensive, where intents recur with family structure, where gold is execution-verifiable, and where drift is real. Earlier corpora each failed one property: FinChain has no store (pure compute), PokeAPI was structurally the wrong regime, CRAG is question-shaped not store-shaped, and SkillCraft is clean and prior-contaminated. OpenTraces is a sealed 11.58GB frozen snapshot of the developer's own trace bucket (1,592 trace envelopes, 861,028 events; seal digest sha256:e7487530..., commit 082269d61). Its credibility rests on construction choices, not assertion: gold is deterministic reference-solver output run twice to byte-identical (gold determinism hash 05c10a26..., never moved across revisions), never an LLM judge; reproducibility was cross-checked against the upstream OpenTraces CLI under HOME-isolation (78/78 sampled checks agree); and a 24/24 Codex adversarial seal audit upheld every sampled gold answer, its single refutation being definitional (session identity) and fixed by sharpening question phrasing, not by changing any gold value. A stale-pointer bug that would have produced wrong distributions (syncable 1,111/481 instead of the true 190/1,402) was caught by a 6-row cross-check discrepancy and never touched the gold solvers. The corpus is also honest about its blemishes: it contains real client slugs, so it is local-only and cannot be pushed without pseudonymization (SEAL-ADDENDUM limitation 6).

**The paired-arm pre-registered methodology.** Arms are compared under a machine-checked parity contract (driver prompts hash identically after the single binding block is stripped), claim sentences are committed before the data exists (git ordering proves it), the cost unit is full-weight model-context tokens with a dollar tie-breaker, confidence intervals are clustered bootstrap over template clusters, and `claimUpheld=false` is defined as a terminal PASS. Every load-bearing number is independently recomputed by a supervisor session from raw artifacts before it counts.

## 4. The negative findings

These are the spine of the program. We foreground them.

**Organic crystallisation does not fire for frontier models within a session.** On the CRAG-finance arc (code-harness-evals Attempts 53-71), Sonnet-4.6 did not reuse a crystallised two-call `df.lib` helper within a session despite crystallisation, availability, a drivable `df.d.ts` signature, and an `AGENTS.md` that named and encouraged the helper. Four runs, `libFunctionsUsed=0` throughout. This reproduces the published null (SkillFlow 0.00, SkillsBench self-gen -1.8pp) on our own substrate. The honest caveat: the decisive reason is structural, the finance mock primitives are always present so a two-call lookup is trivially re-derivable, so the null is regime-bound, not a universal "models never reuse." That is exactly why the corpus choice later moved to SkillCraft, where reuse does fire because tool calls have non-reproducible side effects (R7=0.846).

**The agent refuses the free interface.** Even when affordances are surfaced, the agent's own `df.tool.*` fan-out prior makes it ignore advertised `df.lib`/`df.db` calls (Goal 2 iter5, commit 5d5663650), a direct falsification of "surface the interface and the agent will use it." The agent, not the substrate, is the rate-limiter. Separately, reuse-as-callable fires only outside the shipped default: under the shipped `hooks-candidate-only` mode the reuse half throws, and reuse fires only when the interface mode is permissive AND the preseed prompt is mandate-strength. This matters for honesty: "the model won't call helpers" on the default config is a gate artifact, not a behavioral finding, and the interface mode must always be checked first.

**Cross-session amortisation falsified (the strongest form of "each search gets cheaper").** On the one valid k=5 PokeAPI run (confirm-k5-pokeapi-h1x, 2026-06-03, commit 0665d5a27), with parity held, preseed fired, and crystallise-to-reuse confirmed, arm4 (frozen cross-session warm reuse) cost more than arm1 (inline rewrite, no persistence) in every token unit: full-weight -66,520.8 (168,577 vs 235,098), fresh+output cache-excluded -97 (so not a cached-hydration artifact), dollar-equivalent -6,739.7, with M*=+Infinity and `claimUpheld=false`. It was also less correct (h1x 2/5 vs 4/5). A 33-agent regeneration workflow then refuted three recovery levers with data: the +66k is a turn-count tax not byte bloat (cached-input-per-request is arm-invariant; arm4 just makes +1.8 more turns each re-reading ~36k), fan-out width does not move arm1 turns, and governance-as-correctness on PokeAPI inverted (the numeric gate never organically fired, governanceGatePassed=0/30).

**But we hold this negative honestly in both directions.** It is low-powered: n=6 matched questions, the -66,520.8 marginal is a single cluster with a degenerate point-CI (lower==upper), and the "less correct" sub-claim is McNemar p=0.5 (b=0, c=2). It is a strong directional signal consistent with the within-session null, not a statistically unambiguous result, and the assessment's own critique (G1) says so. And the cost island was conditionally reopened: a $0 ceiling probe (commit d08310f6e) showed a hand-authored deep, invocable helper collapses caller write-cost ~3.5x (caller 20 lines/~183 tokens vs arm1 inline 72 lines/~635 tokens) and clears the cost gate. So the cost pillar died for shallow helpers, not in principle.

**Validity bookkeeping.** Run 1 of the confirmatory series (confirm-k5/, 630 episodes) was INVALID, confounded by harness bugs: arm4 correctness collapsed to 9/90 because a phase-blind binding told phase-1 to call a non-existent `familyFanout` helper, plus 39 invariant violations. Blockers A/B/C were root-caused and fixed (commits 41e3eb77c/1d5f7b05b/355747fb0) before Run 2, which is the real negative. An earlier smoke reuse-null was a fixable mechanism gap (missing preseed mandate plus wrong family), resolved at commit d30903917, not a thesis negative. Distinguishing the confounded runs from the real one is the honesty spine of this section.

**Correctness was never the headline.** Interface virtualisation as a cost lever was proven on a saturated benchmark (P1 matched-arm: -41.3% tokens, neutral correctness, McNemar p=0.25), and FinChain FC3 falsified any correctness win outright (substrate-on and substrate-off make the exact same errors, FAC delta=0, p=1). The surviving value pillars were declared as amortisation, persistence, and governance, not raw correctness, and all four surviving value claims (governance-under-staleness C2, zero-source onboarding C4, deep-helper-TURNS C5, persistence-as-abstraction C8) remain mechanism-proven but endpoint-untested, with zero live verdicts for any of them, blocked on the same unbuilt runner-plus-scorer seam (ASSESSMENT-2026-06-04, commit aa9b72151).

## 5. The one positive result: M5 curated interface on the dark store

This result exists only because organic emergence was killed cleanly first. The original emergence arms terminally failed kill-gate M1 across three honest iterations (scripted-pass ruled INVALID, default-gate fail, pure-compute opt-in fail; RUN-LOG Attempt 5), spending only ~3.2M of 20M driver tokens. Amendment B then replaced "learned" interfaces with a hand-curated one; the word "learned" appears nowhere in the M5 outputs. This is a successful kill-gate, not a failure of the instrument, but it means the positive result is about a curated interface, with emergence deferred to plan 013.

**Headline.** Three arms under a verified parity contract (normalized prompt hash 99cf4d83... identical across arms): armN (cold mount, db primitives only), armR (armN plus one <=600-char template-blind NL recipe, the "good README" floor), armL (armN plus a curated 12-helper callable interface authored from the SCHEMA-TRUTH §6 sketch only, blindness grep zero hits). Over 936 rows (104 questions x 3 arms x 3 seeds):

- PRIMARY upheld: armL 19/104 (18.3%) vs armN 5/104 (4.8%), diff +0.1346, clustered CI [0.0385, 0.2596].
- ATTRIBUTION upheld: armL beats the recipe floor armR (11/104, 10.6%), diff +0.0769, CI [0.0192, 0.1538]. The value is callability, not documentation.
- CO-PRIMARY upheld: armL cheaper in both units, mean tokens 143,518 < armN 157,903 < armR 162,481, mean turns 7.08 < 7.52 < 7.64, at non-inferior (superior) correctness.

**Supervisor recompute-audit.** An independent Opus 4.8 session with its own scorer and RNG reproduced every load-bearing number: all point estimates exactly, both clustered-bootstrap CIs to four decimals under an independent seed (5000 resamples, 26 clusters of 4). Verdict: VALID and reproduces exactly, upheld with one material caveat. The grader was checked for even-handedness (it failed armN seeds with wrong values and passed the one armN seed with correct values using the same normalisation applied to armL).

**The empty-gold caveat (supervisor-only, never in the scorer report).** The absolute margin is disproportionately composed of empty-result (`[]`) questions. Of 104 questions, 11 have empty/trivial gold; on those armL is 3/3 on all 11, and 11 of armL's 19 winning questions are empty-gold. armL also emits a false `[]` on 43 of 279 non-empty question-seeds, a standing empty-set propensity that makes empty-gold a low-information win. The mandate is explicit: the headline is never to be cited without this caveat. The durable claim collapses to the non-empty slice: **armL 8/93 (8.6%) vs armN 0/93 (0.0%) vs armR 2/93 (2.2%)**. The cold baseline never answers a single non-trivial question majority-correct; the curated interface answers eight, of which six are armL-exclusive (the remaining two, otc-0006 and otc-0158, are also majority-correct for armR and so are shared wins, not interface-exclusive).

**Mechanism audit (which helpers carried the wins, and are they verifier-checkable).** The 8 non-empty armL wins cluster onto exactly three curated helpers: `df.lib.spendBy` (otc-0002, otc-0006), `df.lib.sessionsWhere` (otc-0012, otc-0033), and `df.lib.blame` (otc-0153/0156/0158/0160). In every win the answer script is a single helper call with the window/predicate/sha passed in; correctness comes from the helper already encoding the grouping keys, the conjunctive predicate, the session-containment output shape, and the `git_anchor_created` event scan. The baselines failed in four recurring ways against the raw `df.db.records.search` surface: (1) limit-capped or semantically-missed record sets producing wrong sums or empty `[]`/`{}` (otc-0006 under-counts 2026-05-05 sessions 13 vs gold 22); (2) wrong grouping/field schema (armR otc-0002 renamed token fields and split one project into synthetic groups); (3) missing/null answers because the commit-to-trace link lives in `git_anchor_created` events that raw search never surfaces (all four blame rows graded "missing answer value" for armN); (4) hallucinated placeholder ids (armR otc-0033 emitted `session-8`, `session-9`...). Of these eight, two (otc-0006, otc-0158) were also majority-correct for armR, so they are shared wins; the other six are armL-exclusive.

Crucially, every one of these wins is cheaply checkable without knowing the answer. The four blame rows are the strongest case: a verifier re-scans `git_anchor_created` events for the commit hex and confirms a single trace_id, exactly the invariant the grader itself applies. The two spend rows reconcile via control totals (per-group token sums must equal a flat-scan window total; per-group session counts must sum to the window count) plus a disjoint-partition invariant. The two `sessionsWhere` rows re-derive the predicate (every returned row must satisfy the window-plus-conjunction filter; the count must match an independent filter; ids must be real not synthetic). The honest limit: because verifier and helper read the same corpus, these checks prove internal consistency and completeness, not agreement with external ground truth, and so cannot catch a question-intent error shared by helper and verifier. For this benchmark that limit is mild, but it is real and we state it. Note also that this is a hand-reasoned retrospective argument over already-collected rows: no verifier was actually built or executed, so what follows is a proposed promotion mechanism supported by the audit, not a demonstrated result.

## 6. Synthesis: why the product is governed curation, not auto-emergence

Lay the findings end to end and the conclusion is forced. The crystallisation loop works mechanically (the tier flip fires). But (a) the agent will not organically reach for the crystallised surface, (b) when it does, warm reuse does not amortise, and (c) cold agents are wrong 80-90% of the time, so the raw trajectory stream that auto-emergence would mine is mostly wrong work. Mining usage therefore mostly promotes wrong abstractions. This is not a tuning problem; it reproduces the literature verdict ("Library Learning Doesn't", Berlot-Attwell) live on our own corpus, and it is the strongest single piece of evidence that the value is not in the loop but in what gates the loop.

The one thing that demonstrably helped, the M5 curated interface, helped precisely because a human encoded correct grouping keys, predicates, output shapes, and the event-join logic that the cold agent kept getting wrong. The product is the governed accumulation of *correct* abstractions, an evidence layer, not the automatic accumulation of *used* ones.

## 7. The governance problem and the verifier reframe (the heart)

If usage is noise, the central question becomes: what signal is strong enough to promote a helper? The instinctive answer is an oracle, you must know the right answer up front to certify the abstraction. That answer is wrong, and replacing it is the most important conceptual move in the program. We state it as a proposal, because we have not yet built or run the verifier it depends on.

You do not need an oracle. You need a **verifier**: a cheap, independent check that the helper's output is self-consistent and complete against the mounted data. Promotion becomes verifier-survival, not usage-mining. The M5 mechanism audit makes this plausible on real data rather than pure hypothesis, but the verdict is partial and the verifier was never instantiated: the audit is a hand-reasoned argument that for each of the 8 non-empty wins a concrete oracle-free check (event re-scan, control-total reconciliation, predicate re-derivation) *would have* flagged every observed baseline failure mode, empty sets, wrong grouping, missing values, synthetic ids. Whether such checks, once written and replayed, actually separate the wins from the failures is an un-run kill-gate (§9 item 2), not a demonstrated result. The user's role, if the reframe holds, shifts accordingly, from "know every right answer" to "define once per domain what *checkable* means."

A signal ladder for promotion, ranked by how much it depends on an oracle (strongest, least oracle-dependent first):

1. **Cheap independent re-derivation / invariants / reconciliation** (strongest, no oracle): control totals, disjoint partitions, event re-scans. This is exactly what carried the M5 wins.
2. **Self-consistency / convergence across seeds** (free, but can converge wrong): the helper returns the same answer across independent runs where baselines were non-deterministic (the blame rows: 3/3 vs the baselines' stumble-rate).
3. **Sparse human endorsement / active learning** (small ask): promote on a single explicit endorsement event when no cheaper signal exists.
4. **Reuse-survival via quarantine replay** (proves generality, not correctness): the helper replays cleanly on held-out arguments.
5. **Efficiency** (tiebreaker only, never admits on its own): cheaper tokens/turns break ties between already-verified candidates.

The honest boundary: this works in **verifiable-data domains**, reconciliations, aggregations, trace/log analysis with invariants and control totals, where "checkable" has a cheap independent definition. It does **not** work where correctness is contested or where the only check is the same model that produced the answer. We state that boundary plainly because it determines the product's addressable market: datafetch is for domains where a control total exists, not for domains where the answer is a matter of judgment.

## 8. Product recommendation

**The wedge.** A governed evidence layer over a single verifiable-data domain, trace/log/spend analytics is the proven one, given M5. Turn datafetch on over the store, let agents answer questions cold, and promote a helper into the typed surface only when its output survives a cheap domain verifier. Sell the outcome M5 actually demonstrated: a cold agent answers essentially zero non-trivial questions; a governed curated interface answers them and does so cheaper.

**The user's role.** Define the verifier once per domain (the control totals, the invariants, the event-join rules). Not the answers. This is the reframe the go-to-market case rests on, the shift from an unbounded labeling burden to a bounded, one-time domain-modeling task, but it is a hypothesis: whether a domain expert can actually specify those checks in a bounded session, and whether they separate wins from failures, is the un-run kill-gate in §9 item 2.

**Build first:** the verifier-gated promotion path on one verifiable domain, with curated helpers as the seed and verifier-survival as the only admission criterion. Ship the audit trail (visible, cat-able TypeScript helpers) as a first-class feature, because auditability-by-construction is what makes governance trustworthy.

**Do NOT build:** auto-emergence from raw usage (falsified), within-session amortisation as a value claim (falsified), a multi-tenant promotion engine before a single-tenant verifier works, an LLM-as-judge promotion gate (it certifies agreement-with-the-model, the exact failure mode we built deterministic gold to avoid), or anything that promotes on usage frequency.

## 9. Future research agenda

Each item states a hypothesis and the cheapest gate that can kill it for ~$0 before any expensive run.

1. **M7 external validity on held-out questions.** *Hypothesis:* the M5 curated-interface advantage holds on the user's ten real questions, which were deliberately kept out of the pack, not just on the templated questions. (M5 itself ran on a 104-question subset of the 208-question templated pack, 936 rows = 104 x 3 arms x 3 seeds; the 10 held-out real questions are disjoint from both.) *Kill-gate:* hand-run armN vs armL on the 10 held-out questions at k=1; if armL does not beat armN on the non-empty subset, the M5 effect is template-bound and the external claim dies before a full run.

2. **Verifier-elicitation.** *Hypothesis:* a domain expert can specify the per-domain verifier (control totals, invariants, join rules) in a bounded session, and the resulting checks flag the four observed baseline failure modes. This is the gate that converts the §7 reframe from proposal to demonstrated result; it has not been run. *Kill-gate:* write the verifier for the three M5 helper families by hand and replay it against the existing 936 M5 rows; if it does not separate the 8 wins from the baseline failures, verifier-elicitation is harder than claimed and the promotion-path argument does not yet stand.

3. **Active-learning promotion gate.** *Hypothesis:* promoting only on verifier-survival (ladder rung 1), falling back to a single endorsement event (rung 3) when no cheap check exists, beats promoting on usage. *Kill-gate:* simulate both policies offline on the M5 trajectory stream; if usage-promotion and verifier-promotion select the same helper set, governance adds nothing here and the gate is decoration.

4. **Cross-session persistence under staleness (C4).** *Hypothesis:* governed reuse strictly dominates an ungoverned-persistent arm under source drift (where arm1 inline re-derivation is drift-immune and so not the right comparator). *Kill-gate:* the committed $0 drift kill-gate (commit 3e89be8dd) on a numeric corpus where the FAC gate actually passes; note the real DONE-INVALIDATED risk (0/16 df.lib reuse precedent, governance gate 0/22 live), so screen the hardest template for control-arm error rate r>0 first.

5. **Zero-source SDK onboarding (C2, highest promise).** *Hypothesis:* `datasetInit.ts` compiles a new dataset to a typed learnable surface with zero per-dataset source, measured in src-lines/human-edits per dataset rather than per-task tokens. *Kill-gate:* the mechanism is already proven (sac-zero-src-onboarding.test.ts); the cheapest kill is to onboard one genuinely new store end-to-end and count human edits, if it needs hand-written per-dataset glue, the "zero-source" claim is false.

## 10. Methodological lessons

These are reusable independent of the verdict.

- **Pre-registration before data.** Claim sentences and predicted curve shapes were committed before each run (M5 prereg in commit fa6ed7277 precedes the M5 result in d246753eb), so no result could be retrofitted to the data.
- **Cheapest-NO-first kill gates.** Gates are ordered so the experiment that can most cheaply say NO runs first, and `claimUpheld=false` is a terminal PASS. M5 spent only ~3.2M of 20M driver tokens before the emergence loop was killed, never buying the full run before the premise was proven.
- **Supervisor recompute-audit.** No number counts until an independent session re-derives it from raw artifacts. This caught real defects (the amortisation ledger was reproduced byte-for-byte; the cross-arm audit found a cache-token bug, a dual-gate, and a benchmark-key leak) and produced the empty-gold caveat that the scorer report missed entirely.
- **Negatives as PASS, not re-inflated.** The amortisation falsification was carried with its own low-power caveats verbatim (n=6, degenerate CI, p=0.5) and with the counter-evidence that reopens the cost island, avoiding a one-sided read in either direction.
- **Delegated gates need substance criteria.** A build agent made plan-012 M1/M2 "pass" by seeding an answer-key dispatcher, measuring obedience not learning; the run was ruled INVALID. The lesson: pin seed/scaffold contracts, authorship requirements, and the exact column a threshold is evaluated on, not just the mechanism.
- **Own-`claude -p` billing.** All measured drivers run on the user's own subscription login (`claude -p --model claude-sonnet-4-6 --safe-mode --no-session-persistence`), never an API key; rate-limit episodes are marked INCOMPLETE and retried, never graded.
