datafetch — explainer · 2026-05-18

A substrate that turns agent code into learnable execution surface

datafetch is a dataset harness for coding agents. The agent writes a TypeScript snippet against a typed df.* runtime; every primitive call is captured into a trajectory; an observer crystallises recurring compositions into typed helpers (df.lib.<name>) that subsequent episodes see and reuse. This page documents the committed implementation, how it scored against the alternatives, and what is still open.

The honest summary
The substrate's contribution under a strong agent backend (Claude sonnet-4-6) is repeated tool-fanout consolidation that drops per-task tokens by ~40% and wall-clock by ~17% while keeping correctness within noise. Pass-rate headroom on this backend is too narrow at low effort to show a correctness signal; cost is where the substrate measurably lifts.

02How it works — the workspace contract

Every episode runs in a mounted intent workspace. The harness builds it from a template, the agent fills in scripts/answer.ts, the runtime replays it through the snippet sandbox, and the observer reads the resulting trajectory off disk.

Tenant-persistent state lives under DATAFETCH_HOME. Each episode mounts a fresh workspace with typed handles, a warm-start lib/ mirror, and the runtime answer-kit. After the snippet runs, the observer reads the trajectory off disk and authors new helpers into the cross-episode lib/.

03The runtime — what df.* exposes

The df global is constructed by buildDf() in src/snippet/dfBinding.ts (line 74) and injected as globalThis.df before each snippet runs. Every primitive call is proxied through a recorder, so a complete trajectory is captured as the snippet executes.

PrimitiveWhat it doesWhat gets recorded
df.db.<ident>.findExact / search / findSimilar / hybrid Resolves to a mounted dataset collection and calls the adapter db.<ident>.<method>
df.tool.<bundle>.<tool>(input) Shells out to invoke-skillcraft-tool.py; memoised within a run tool.<bundle>.<tool>
df.lib.<name>(input) Routes via HookRegistry (or LibraryResolver in legacy) lib.<name>
df.answer(input) Pure constructor of AnswerEnvelope (not recorded)

Every db.* and tool.* call passes through trajectory.call(primitiveLabel, input, exec, scope) which captures input, output, duration, and nesting scope into the TrajectoryRecorder defined in src/trajectory/recorder.ts.

04The crystallisation pipeline

A trajectory is saved to disk; the observer fires; the gate decides what survives; the author writes a typed TypeScript file under lib/<tenant>/ that becomes callable as df.lib.<name> on the next episode.

The seven gate checks live in shouldCrystallise() (src/observer/gate.ts line 82). The intent-convergence threshold of 2 is what makes the loop "Goal 4-honest" — first occurrence records but does not yet crystallise.

The seven gate checks

  1. Phase must be execute or commit (plan attempts excluded).
  2. Trajectory slice must have ≥ 2 primitive calls.
  3. errored false and no call output looks like an error.
  4. Mode must be novel or interpreted (not LLM-backed or cached).
  5. Substrate-rooted chain: a db.* list-returning call with a downstream lib.*/tool.* that structurally consumes it.
  6. Shape-hash dedup against existing lib/<tenant>/.
  7. Intent convergence: convergenceCount ≥ 2 (default).

Why this matters
These are not "tricks to score points on the benchmark." Each one is a generic typed scaffold that lifts a real class of runtime errors out of agent-authored code. The pattern — author tries the obvious thing, gets bitten by a payload shape or coercion edge case — is the same pattern you see across REST integrations in the wild.

The open architectural diagnosis
The substrate's infrastructure (observer, seed, df.d.ts, AGENTS.md, lib/ overlay) now transfers off SkillCraft cleanly — the substrate-decouple work (May 2026) moved the four answer-kit rewriters into src/runtime/answerKit.ts, renamed the SkillCraft-coded tool bridge to a generic toolBridge with a required runnerPath, and parametrised the observer's identifier-attribute heuristic. P2 itself (at the time of writing) ran through a SkillCraft-shaped fake bridge; that coupling has since been removed. The substrate's crystallisation policy remains the open issue: it authors helpers thin enough that agents prefer re-deriving inline. The auto-crystallised toolFanout packages a 3-call fan-out into a one-liner — but the agent's inline Promise.all reflex is equally short. Hand-authored helpers with rich frontmatter (userPostSummary) do get reused. Fix queued as B2.

Before iter164, the team ran a structured battle-of-ideas on four competing hypotheses about why the learning loop failed at scale. Two arms won and are committed; two were scaffolded and remain inert at current scale. Several adjacent academic ideas were considered and deferred.

Scaffolds that are inert at current scale

Coverage-density gate in src/observer/gate.ts. Helpers whose min(steps,6) × distinctTools / 6 < 2.0 are tagged narrow. All five current helper templates pass by construction, so the env flag is non-moving. Full ReGAL semantic replay (execute refactored program, compare outputs) deferred.

V2 PSN maturity state machine

Per-helper FSM candidate → verified → preferred ↔ suspect → quarantined in score-r1-r9.ts L245-422. Promotes after 2 passes, demotes after 3 consecutive cost-drop losses. At 36-row probe scale each helper gets too few uses; needs full-126 to be observable.

Cache qualification — strict-zero vs framework-bounded

The original Goal 4 cache rubric required agentCachedInputTokens === 0 on every row. This is structurally unachievable with claude --print: Anthropic's inference backend caches the framework system prompt and tool definitions server-side, and that caching cannot be disabled by the caller. The 2026-05-17 Codex adversarial review also caught a normalizer bug that had been silently dropping agentCachedInputTokens, making the iter164 "0/126 cache nonzero" headline a measurement artifact. Real value: 126/126 with cache > 0.

The reframe accepted on 2026-05-17 — cacheBoundedByFramework — rejects only inter-episode state leak inside the substrate (a learned helper grown too large, an accumulating lib-cache, a resumed session), operationalised as agentCachedInputTokens ≤ 250k per row. The strict reading lives on as CACHE_QUALIFICATION_STRICT=1 but is treated as unachievable on this backend.

10Open issues & next moves

The three caveats that survive into the next phase, and the three overnight goals B1/B2/B3 from experiments/PLAN.md.

Caveats that survive

  • iter164 MET was fragile. Anthropic API health is the dominant variable: iter161 (same substrate, ~24h earlier) had 114/126 500-errors and scored R1=0.48 / R3=0.29. Single-shot MET; not yet replicated.
  • Crystallisation policy is too permissive. Auto-crystallised thin helpers don't beat the agent's inline-rewrite reflex (P2). Narrow the convergence gate to compositions that meaningfully exceed inline cost; add the insight annotation for selective discovery.
  • codex-direct full-126 is still 6/8. Goal 4 MET is Claude-specific; the compositional cluster shapes need authored templates the substrate doesn't yet produce.
